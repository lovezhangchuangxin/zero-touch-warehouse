# 订单与物流合同

本篇记录上一轮订单讨论的推荐基线，细节仍可调整。

## 获取订单

系统持续向订单市场发布有限数量的物流合同，玩家通过界面或代码查询并自主接受。默认自动派发为强制任务不是当前基线。

- 界面和代码查询同一份已公开订单列表，不暴露无限未来的合同。
- 未接受的合同有接单期限，过期离开列表，不受处罚。
- 接受后才承担履约责任，无须竞价。
- 可通过自动接单策略降低操作负担；是否提供内置开关待定，教学至少提供代码策略。
- 接单检查基础资格，例如装卸口与违约责任承担条件；具体资格规则待定。
- 实际仓容、机器人能力与未来拥堵由玩家评估，系统不代替玩家保证可履约。
- 接单是管理操作，不消耗机器人动作，tick 结束结算，下一 tick 查询结果。

## 合同包含完整物流承诺

玩家接收客户货物，暂存并按计划交付，赚取物流服务费，不买卖货物。

接受合同同时承诺入库和出库。由合同产生的车辆运输任务不再单独接取，避免玩家只接入库、不交还货物。

首期每份合同对应一辆入库车和一辆出库车，两者货物种类及数量一致。不同合同可以并行，入库与出库时间交错。以后再考虑一批入库、多次提货。

## 信息模型

下列名称表达数据含义，不规定最终字段命名。

| 信息 | 内容 |
| --- | --- |
| 标识 | 唯一订单 ID |
| 货物清单 | 每种货物的类型与箱数 |
| 接单期限 | 最晚可接受的 tick |
| 入库安排 | 入库车辆到达 tick、卸货截止 tick |
| 出库安排 | 出库车辆到达 tick、装货截止 tick |
| 基础报酬 | 完成整份合同的物流服务费 |
| 延误条款 | 宽限时间、每 tick 扣减、扣减上限 |
| 失败条款 | 最终失败时间或条件、损失规则 |
| 当前状态 | 可接、待入库、入库中、存储中、出库中、完成、失败；未接过期可标为已过期 |
| 履约进度 | 已卸、已交、剩余货物数量 |
| 关联对象 | 入库车 ID、出库车 ID，以及靠泊后的装卸口关联 |

合同条款与动态履约数据分开。车辆尚未生成或尚未靠泊时，关联数据的空值语义需要在接口设计中明确。

## 货物归属

每箱货物绑定所属合同。即使类型相同，不同合同的箱子也不能互相替代交付。界面显示类型与合同归属，代码提供对应查询。

## 时间与车辆

第一版接单时公开准确的到达和截止时间，不引入随机提前到达、车辆故障或临时改需求。

车辆“到达”指进入仓库外等待队列；只有“靠泊”之后才能装卸。排队时间计入履约时间，因此订单的到车高峰会竞争装卸口。

初期由系统分配空闲装卸口。多装卸口阶段可考虑开放代码指定靠泊位置与排队优先级，具体纳入首期与否待定。

正常流程为：可接 → 待入库 → 入库中 → 存储中 → 出库中 → 完成。异常、部分卸货、部分装货、超期和车辆离场的完整状态转移仍待补齐。

## 示例合同

以下数值仅说明信息结构，不是平衡参数。

| 条款 | 示例 |
| --- | --- |
| 合同 | #102 |
| 货物 | A 类 6 箱、B 类 4 箱 |
| 接单截止 | tick 120 |
| 入库安排 | tick 150 到达，tick 210 前卸完 |
| 出库安排 | tick 400 到达，tick 460 前装完 |
| 完成报酬 | 200 金币 |
| 延误 | 每 tick 扣减奖励，最多宽限 60 tick，随后按失败条款处理 |

截止 tick 是否包含当 tick 的动作，以及宽限分别如何适用于入库、出库，需要统一定义。

## 收益与违约

当前基线为完成整份合同后统一支付，不在卸完货时先支付可反复获取的入库收益。

报价主要考虑货物数量、存储时长和时间紧迫程度。长存储合同占用货位，急单占用调度能力，使接单有实际取舍。

延误先扣减奖励；最终失败的罚款、已完成部分是否结算、剩余货物回收方式仍待设计。失败必须有清退货物和恢复经营的途径，不能让客户货物永久占满仓库。
