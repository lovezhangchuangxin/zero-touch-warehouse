# 首期范围与待定事项

## 首期设计基线

- 单机 2D 网格仓库，全局视角。
- 固定大小仓库，先通过增加设备扩容；地图扩展暂不纳入基线。
- Python / JavaScript 同步程序，初始化后每 tick 调用 `loop()`。
- API 统一挂在 `Game` 全局对象上，两种语言同名 snake_case；管理操作即时生效。
- 单箱载重机器人，移动、取货、送货、放下、拾起、充电。
- 货架（基线每货架四箱）、充电桩、通用装卸口。
- 少量货物类型，箱子占用的存储空间相同。
- 常驻商品市场（`Game.market`）：买入卖单、卖出买单赚取差价，装卸位占用即压力。货物按类型通用，支持主动销毁。
- 商店购买、受约束的销毁与部分退款。
- 持续经营、教学引导、暂停、单步、变速、存档和动作诊断。

## 首期不考虑

- 迷宫等额外小游戏：用户明确留待后续。
- 传送带、维修、员工、复杂商品价格：当前建议暂缓。
- 电池老化、浮动电价、货物重量体积差异、保质期和品质。
- 随机车辆故障、挂单撤回与改价、指定装卸口接单。

## 实施前优先确定

| 主题 | 未决问题 | 影响 |
| --- | --- | --- |
| 初始经营 | 地图尺寸、初始金币（须覆盖市场最便宜整单） | 首笔交易能否启动 |
| 装卸口 | 占地尺寸、边界限制、交互面 | 地图与寻路 |
| 交互冲突 | 多机器人争抢同一货物或容量、转交与其他动作同时发生 | 数据一致性 |
| 充电冲突 | 多机器人同时请求同一个充电桩 | 调度策略 |
| 市场生成 | 价格波动模型、挂单数量与刷新节奏、价差结构；含保证暂存必要的结构性参数（如买卖数量错配） | 交易玩法深度 |
| 程序异常 | 错误或超限时已提交指令如何处理 | 调试与原子结算 |

## 随原型继续确定

- 电池容量、充电速率、动作耗电、设备价格、每货架容量、销毁退款比例、借贷利率与信用额度（额度须高于购置一台机器人的成本）、取消手续费比例（应大于短期典型价格跌幅，必要时随接单后 tick 数递增）。
- `buy` 取值表、`_move` 缓存格式、路径过期与可视化、顶层常量别名等 API 细节，见 [API 设计](08-api-design.md) 待定节。
- 市场参数：价格波动幅度、挂单量与刷新节奏、价差与各类型起始定价。
- 是否提供内置自动接单开关。
- 教学关卡数量、解锁顺序、教学到持续经营的衔接；初始化阶段是否允许提交动作；两种语言切换细节。
- 动作结果记录的最终字段、路径查询的成本限制、持久化数据格式和沙箱限制。

## 原型验证目标

1. 一台机器人可以完成接单、卸货、存储、充电和交付的闭环。
2. 增加到约五台机器人时，任务分配和交通调度能显著影响效率。
3. 货架每格容纳多箱，相对地面暂存节省空间，地面暂存有通道占用代价。
4. 买卖价差与仓容限制使囤货、快转与直通转运成为真实取舍。
5. 单步执行和错误信息能让玩家解释机器人为什么没有按预期行动。
6. 买错货或周转失灵时，销毁与市场回购提供明确的恢复经营途径。

这些目标用于评估玩法，不等同于已经通过的测试。
