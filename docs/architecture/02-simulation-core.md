# 模拟核心与确定性

## 世界线程与 tick 状态机

`World` 由世界线程独占，每个 tick 串行经过固定阶段，语义对齐 [Tick、动作与电力](../game-design/03-simulation-and-actions.md)：

```
1. tick 边界事件    车辆到场、市场刷新
2. 产出查询视图    含上一 tick 结算结果（last_result）与宿主查询镜像（见 [03](03-player-runtime.md)）
3. 调用 loop()     经宿主进程执行：玩家查询本地镜像、提交动作（受理制）、执行管理操作（即时生效）
4. 统一结算        冲突裁决 → 动作执行 → 车辆离场 / 收款 / 释放装卸位（结构见「结算三段式」）
5. 计息、追加诊断事件、产出渲染快照，tick 序号 +1
```

- 阶段 3 中玩家代码出错或超限时：已受理动作与已生效管理操作照常进入阶段 4，之后世界暂停并报错（见 [03](03-player-runtime.md) 故障分级）。
- 阶段内顺序细则（车辆出现于 `loop()` 之前、离场与收款同结算内完成等）以 [玩法设计 03](../game-design/03-simulation-and-actions.md) 为准。
- 界面命令在世界线程的固定安全点执行：运行中，管理命令（购买、销毁）在上一 tick 阶段 5 结束之后、本 tick 阶段 1 边界事件之前生效——严格位于 tick 之间，按 FIFO 执行并记录各自生效的 tick，其效果对本 tick 边界事件可见（如新购装卸口可被本 tick 到场车辆占用）。暂停且没有执行中的 tick / 初始化时立即生效；单步执行期间排到该 tick 结束。会话命令（暂停、变速、存档）在安全点生效，宿主紧急终止走独立控制路径。玩家代码内部发起的管理操作不受此规则约束，仍即时生效。
- 查询视图不另建副本：Player Phase 的正式 World 只被管理操作修改，机器人意图在结算前不落地，live World 本身就是玩法要求的查询语义（tick 开始状态 + 已生效管理操作）；"生成 tick 快照"是逻辑概念，实现上指 last_result 发布与宿主查询镜像产出（见 [03](03-player-runtime.md)），不维护独立的快照拷贝或管理增量日志。

## 结算三段式：受理 → 求解 → 原子提交

阶段 4 在代码结构上固化为三段，语义仍以 [玩法设计 03](../game-design/03-simulation-and-actions.md) 为准：

1. 意图收集：受理通过的动作构成本 tick 意图集合，每机器人至多一条，集合本身与提交顺序无关。
2. 求解（只读）：在最终管理状态上完成重新校验、落点候选、移动依赖求解与按 id 升序的资源占用推演，产出完整结算计划；求解过程不修改正式世界。
3. 原子提交：计划一次性应用，连同车辆离场、订单完成、收款与装卸位释放按既定顺序落地，统一产出结算结果与诊断。

求解阶段是「最终世界状态 + 意图集合 → 结算计划」的纯函数：管理操作集合固定时，任意提交排列得到同一计划。计划须保留 id 升序的资源占用次序，不做成无序变更集；"结算内依次完成"的离场与收款顺序不可重排。

## 确定性规则

同平台同版本下，模拟核心对相同完整初态、PRNG 状态和有序输入序列产生相同结果。玩家代码运行的复现还要求相同初始化 / 重载时序及确定的玩家程序输入，不能仅凭源码相同推断轨迹相同：

| 规则 | 内容 |
| --- | --- |
| 随机源 | 模拟内一切随机使用固定种子的伪随机数生成器（PRNG，xoshiro 家族）；按子系统独立分流（市场、装卸位分配、场景），各流自世界种子与固定子系统标识派生、状态分别入存档，单一子系统实现的变更不扰动其他流的轨迹；具体算法与状态字节布局随存档格式冻结，变更须迁移旧档；禁止系统随机与系统时间 |
| 时间 | 当前 tick 序号是唯一时间概念；市场波动、装卸位分配只依赖 tick 序号与 PRNG |
| 遍历序 | 一切集合遍历按 id 升序（BTreeMap 或显式排序），不依赖哈希表迭代顺序；以 CI 双跑一致性测试兜底（见 [08](08-validation.md)） |
| 数学 | 权威经济值（余额、欠款、订单价、手续费、利息）以定点整数存储与运算（内部最小单位为金币千分量级，i64）；f64 只用于市场模型的中间计算，进入世界状态前按固定舍入规则（half-even，随规则与存档版本冻结）量化。f64 存"分值"不是替代方案——0.01 在二进制中不可精确表示。不调用语言运行时的数学函数；API 暴露侧见 [04](04-api-bindings.md)。玩家计算可影响提交指令，因此运行时复现还须约束玩家侧输入与非确定来源 |
| Game.memory | 主进程有序数据树，表示及修改规则见 [06](06-persistence.md)，存档往返保持键序 |

- 复现承诺不含超限介入的 tick：墙钟预算本身不是确定量，临界代码可能一次通过一次超限（性能不同的机器之间同样如此），回归测试对此放宽。预算触发的暂停在诊断与界面上明确归因为执行预算，不与模拟不确定性混同。
- 跨平台、跨版本不承诺逐字节一致（单机游戏无此需求）。

## 输入记录与复现边界

- 外部管理命令记录来源、命令编号、参数、生效 tick、安全点内序号和结果。代码加载 / 重载 / 语言切换记录源码哈希及可取得的源码版本；场景与规则版本同样属于输入。
- 调试复现包包含起始世界与 memory 检查点、版本信息以及区间内变更型 Game 请求 / 结果、UI 输入、初始化提交、执行关闭原因和最后提交号；本地镜像应答的查询是世界状态的纯函数，无需记录。常规记录采用有界缓冲，超过容量明确标记截断；完整复现测试必须从检查点开始且没有缺口，首期不承诺无限历史回放。
- 模拟测试直接重放输入，不运行玩家语言；运行时测试使用固定重载时序的确定性程序。任意普通全局变量在重载 / 读档后都可改变行为，不要求与不中断运行等价。仅把持久控制状态放入 memory 且初始化幂等的专用测试程序用于恢复等价测试。
- 自主执行的墙钟超限可能落在不同请求之间，不要求两次自然超限轨迹相同；重放已记录的截断位置时必须得到同样状态。运行预算与随机源是两个不同问题。

## 状态快照与诊断事件

- 渲染快照只携带最新可见状态、tick、世界修订号、最近事件序号；不可变、缓冲有上界，同一时刻最多一帧在途。前端按修订号确认消费，慢时合并丢弃旧状态，不反压模拟；暂停时管理操作也增加修订号并发布状态。
- 诊断事件单独存入主进程有界环形缓冲，不随渲染快照丢弃。记录单调事件序号、tick、阶段、来源、机器人 / 订单 id、请求号、动作参数与结果码；错误事件附可取得的源码信息。
- 前端按事件游标分批拉取 / 确认，允许重试并去重。若游标早于保留范围，返回明确 gap（缺失起止序号），界面显示“部分历史已过期”，不假装历史完整。事件条数与字节双重限额，生产快于消费时覆盖最旧记录。
- 受理失败、结算结果、管理操作、订单完成、运行时故障均有诊断记录；`last_result` 仍只有上一 tick 受理成功动作的结算结果，不承担完整历史。日志有单独配额，刷屏不能挤掉全部故障记录；故障摘要独立保留最近一次。
- 首版 JSON；用前端慢消费和快进压力测试校准容量、批大小与快照频率，再考虑二进制编码。诊断环不替代完整复现包。

## 场景、规则配置与教学

场景定义初始地图 / 对象、种子、经济和设备参数、可用能力、教学目标及提示。内容带 id 与版本，加载时校验合法占位、资金、目标引用及参数边界；由 `sim` 的场景加载入口产生 World，教程与持续经营共用动作结算规则，不在前端另写规则。

目标判定在 tick 结算后及暂停管理操作安全点执行，读取世界与事件；阶段进度、已触发提示标志进入存档。前端只展示目标和解释。重开从场景初态重建世界、PRNG 与 memory，并重新初始化程序；默认保留玩家源码，恢复示例代码是单独操作。教学转持续经营由显式场景转换定义哪些世界 / 程序 / memory 保留，不由 UI 隐式拷贝；转换细节随第一条教学链冻结。

## 变速与暂停

| 模式 | 行为 |
| --- | --- |
| 暂停 | 世界线程不推进 |
| 单步 | 推进一个完整 tick 后回到暂停 |
| 常速 / 快进 | 按目标 tick 频率推进；玩家代码每 tick 全额执行，快进的实际频率受每 tick 实际耗时约束，达不到目标频率时连续推进 |

## 待定

- 常速与快进的默认 tick 频率（参考值：常速 1–10 tick/s、快进 50–200 tick/s，随界面观感与每 tick 实际耗时校准）。
- 渲染快照字段、诊断缓冲容量与事件字段结构（随 [API 设计](../game-design/08-api-design.md) 的 `last_result` 结构一起冻结）。
