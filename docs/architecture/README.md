与玩法设计目录一致：**已定**表示讨论确定、作为实现前提；**待定**表示实现前需要补齐的细节，散布在各文档的"待定"节。

## 已定决策

- 技术栈：Tauri 2 + Rust + Vue 3 + TypeScript + Pixi.js（WebGL）。
- 双原生进程：主进程持有世界状态与结算；玩家代码在独立的宿主进程（runtime host）中执行，可随时终止重启。主进程健康时宿主故障不回滚已提交世界与 Game.memory；未提交调用可能丢失，多调用部分完成须对账；主进程崩溃从有效存档恢复；webview 是纯视图层。
- 双语言运行时均为进程内嵌：JavaScript 走 rquickjs（内嵌 quickjs-ng），Python 走 PyO3（内嵌 CPython）。
- Game API 在 Rust 中单点定义，生成双语言绑定、类型存根、编辑器补全与文档。
- 沙箱目标是资源可控（内存、执行时间、能力面），不防恶意攻击（理由见 [03](03-player-runtime.md)）。
- 普通全局变量只跨 tick 保留；跨热重载（玩法设计称"代码重载"）与读档持久的只有 `Game.memory`。
- 目标平台仅 Windows 与 macOS 的主流版本，不支持 Linux（含 Steam Deck）。

## 架构原则

1. **世界状态唯一权威在 Rust**。前端只读渲染，玩家代码只能通过 Game API 访问。
2. **确定性**：同平台同版本下，相同初态、随机状态和完整输入序列得到相同模拟结果；重载、UI 操作与故障边界也属于输入。
3. **失败可解释**：一切超限与异常都转为玩家可读的错误并暂停世界——已受理的动作照常结算、推进到 tick 边界后暂停（见 [03](03-player-runtime.md) 故障分级）。
4. **双语言契约一致**：签名与结果码同源生成，值模型和生命周期由共享黑盒用例验证。

## 规范归属

动作受理与资源冲突以玩法 03 为准；memory、恢复与存档以架构 06 为准；IPC 提交点以架构 03 为准；架构 02 定义阶段和外部输入。引用处不另立近似规则。性能数字都是待测目标，验收证据需记录平台、版本、配置与测量结果。

## 本轮优化取舍

- 保留双语言、Rust 权威世界、独立宿主及 Vue / Pixi 分工。
- memory 改为主进程受控树，承担同步读写与包装器的实现成本，换取宿主崩溃不回退已提交记忆；原型 A 必须量测该成本。多条 API 不组成事务，恢复对账进入教学。
- 动作受理不预占共享资源，结算采用显式优先级与不递补规则；充电统一为逐 tick 申请，避免跨 tick 锁定状态。
- Position 持久化只保留坐标值；类型还原不靠猜测。双语言一致性由值模型和黑盒测试约束。
- 可玩多机器人闭环提前，打包风险尽早冒烟；完整发布工程不阻塞第一次玩法验证。
