单机（b2-one + demo_one.js）：tick 80 六单全清，金币 311.60——五机分流版
与单机同拍完成（83 tick，多出的 3 tick 是待命机让道行军）。

naive 的堵塞形态（事件面板逐条可解释）：

- tick 1~5 五台同时 `market.take` 同一张单：1 台 OK、其余 `ORDER_TAKEN`
  受理失败；两口被占后继续抢单的收到 `NO_FREE_PORT`。
- 五台涌向同一个交互站位 (1,4)：后到者 move 结算 `CELL_CONTESTED`。
- 交互列 x=1 对穿互换：成对 `CHAIN_BLOCKED`（settle 对二元交换环双负，
  docs/game-design/03）。
- 约 tick 6 起五台互为环环相扣的路障，全场冻结——受理仍通过（返回
  OK）但结算必败，机器人"以为"自己在走，面板上每 tick 的
  CHAIN_BLOCKED 流水解释了为什么原地不动。

## "玩家修改代码解决堵塞"验收

从 naive 到 lanes 的三处改法（对应上面三个堵塞形态）：

1. 抢单冲突 → 认领闸门：`my_orders` 非空不接新单（串行流水）；
2. 站位/通道互挤 → 让出主通道：待命机开场同向东进各自泊位后静止；
3. 对穿死锁 → 单一 worker 独占工作区，全场无对向流量。

教训（写进示例脚本注释）：move 受理通过 ≠ 移动成功，结算可能在
CELL_CONTESTED/CHAIN_BLOCKED 落败；判断"上 tick 白走"要看
`r.last_result`。本图两口窄道并行卸车只会互相穿行——错开任务比抢
并行更能提高吞吐。

## 桌面应用冒烟记录（2026-09-13）

`pnpm app:dev` + `cargo run -p ztw-desktop`（devUrl :5180）：

1. 启动即见画布（墙瓦、门洞留空、货架叠箱、装卸口与车辆足迹、充电桩、
   机器人三态精灵）与面板（机器人电量/携带/last_result、市场四单、金币
   300.00、事件/日志页签）。
2. 载入示例"单机全闭环" → 保存并重载 → 顶栏翻为已加载 → 运行 5×：
   tick 推进、金币流水 300 → 293.60 → 311.60，事件面板滚动可见
   结算（pick/move/give → OK）、管理（接单扣款与余额）、订单完成
   （收款与余额）三类事件，与模拟权威逐笔对账一致。
3. 暂停按钮：顶栏立即翻"已暂停"（控制面帧经快照通道送达）；恢复运行。
4. 故障链路（未在本次冒烟重复，由 world_thread 集成测试覆盖）：坏代码
   → script fault 自动暂停 + 故障横幅（last_request_id/last_op 可见）→
   热重载修码 → 持续运行；终止宿主走独立控制路径并归类
   host_terminated:KILLED_BY_MAIN。

## 已知偏差

- 车辆素材 1×2 足迹而逻辑 1×1 锚点格：画布以装卸口格为锚按朝向伸出
  第二格，不改模拟（docs 待定项）。
- lanes 版实际由 worker0 单机完成全部订单：本图两口窄道下并行收益为
  负（naive 即反例），"显著改变吞吐"以让道 + 串行流水达成。
